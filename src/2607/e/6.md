# E6 Простая среда выполнения

<!--
You have already implemented the minirv NPC in RTL, but it can only run some very simple programs. To run more complex programs, we need to compile programs that can run on minirv. For this purpose, we provide a project named `abstract-machine`, or AM for short, for building programs. This project provides a bare-metal runtime environment, offering the necessary support for programs to run directly on the processor, that is, in a bare-metal environment.
-->
Вы уже реализовали NPC miniRV на RTL, но он может выполнять лишь очень простые программы. Чтобы выполнять более сложные программы, нам нужно компилировать программы, способные работать на minirv. Для этого мы предоставляем проект под названием `abstract-machine`, или сокращённо AM, для сборки программ. Этот проект предоставляет среду выполнения bare-metal, обеспечивающую необходимую поддержку для запуска программ непосредственно на процессоре, то есть в среде bare-metal (без ОС).

Короче говоря, чтобы запустить программу `dummy` на NPC miniRV, вам также нужно:

1. Изменить значение сброса PC у NPC на `0x80000000`.
2. Изменить `pmem_read()` и `pmem_write()` так, чтобы они обращались к массиву памяти по смещению между параметром `addr` и `0x80000000`.

## Постройте процесс пакетного запуска программ

<!--
Soon you will need to run many programs to test NPC more thoroughly. If you have to manually specify the program to run every time and manually judge whether the result is correct, the process will be very inefficient. Therefore, you need to build a flow that supports automatically running programs in batches, so that you can run various programs efficiently.
-->
Скоро вам понадобится запускать множество программ, чтобы тестировать NPC более тщательно. Если каждый раз вручную указывать программу для запуска и вручную оценивать, верен ли результат, процесс будет очень неэффективным. Поэтому вам нужно построить процесс, который поддерживает автоматический пакетный запуск программ, чтобы вы могли эффективно запускать различные программы.

<!--
We previously agreed that a program ends after executing the `ebreak` instruction. However, programs compiled on AM do not contain the `ebreak` instruction, and manually inserting an `ebreak` instruction into every program in the simulation environment is inefficient. In fact, we can insert this `ebreak` instruction into the `minirv` runtime environment. After doing so, all programs compiled to `minirv` through AM will automatically contain the `ebreak` instruction.
-->
Ранее мы условились, что программа завершается после выполнения инструкции `ebreak`. Однако программы, скомпилированные в AM, не содержат инструкцию `ebreak`, а вручную вставлять инструкцию `ebreak` в каждую программу в среде симуляции неэффективно. На самом деле мы можем вставить эту инструкцию `ebreak` в среду выполнения `minirv`. После этого все программы, скомпилированные под `minirv` через AM, будут автоматически содержать инструкцию `ebreak`.

<!--
But the `halt()` function in AM is C code. To insert the instruction we want into it, we can use an [inline assembly statement](http://www.ibiblio.org/gferg/ldp/GCC-Inline-Assembly-HOWTO.html):

```diff
--- abstract-machine/am/src/riscv/npc/trm.c
+++ abstract-machine/am/src/riscv/npc/trm.c
@@ -17,3 +17,4 @@
 void halt(int code) {
+  asm volatile("ebreak");
   while (1);
 }
```
-->
Но функция `halt()` в AM — это код на C. Чтобы вставить в неё нужную нам инструкцию, мы можем использовать [встроенную ассемблерную вставку](http://www.ibiblio.org/gferg/ldp/GCC-Inline-Assembly-HOWTO.html):

```diff
--- abstract-machine/am/src/riscv/npc/trm.c
+++ abstract-machine/am/src/riscv/npc/trm.c
@@ -17,3 +17,4 @@
 void halt(int code) {
+  asm volatile("ebreak");
   while (1);
 }
```

<!--
Next, let's consider how to automatically determine whether the program has executed correctly. For this purpose, we define the following convention: before a program terminates, it first writes an integer representing the termination status into the `a0` register, and then executes the `ebreak` instruction. If this integer is `0`, it means the program terminated correctly; if it is not `0`, it means an error occurred in the program.
-->
Далее рассмотрим, как автоматически определять, корректно ли выполнилась программа. Для этого мы определим следующее соглашение: перед завершением программа сначала записывает в регистр `a0` целое число, представляющее статус завершения, а затем выполняет инструкцию `ebreak`. Если это число равно `0`, значит программа завершилась корректно; если оно не равно `0`, значит в программе произошла ошибка.

<!--
To implement this convention, on the one hand, we need to modify the instruction sequence at program termination to ensure that the `a0` register holds the program's termination status before the `ebreak` instruction is executed. We only need to slightly modify the inline assembly instruction above: `asm volatile("mv a0, %0; ebreak" : :"r"(code));`. After this modification, before executing the `ebreak` instruction, the inline assembly first moves the value of the variable `code`, which represents the program's termination status, into the `a0` register.
-->
Чтобы реализовать это соглашение, с одной стороны, нам нужно изменить последовательность инструкций при завершении программы так, чтобы к моменту выполнения инструкции `ebreak` регистр `a0` уже содержал статус завершения программы. Для этого достаточно немного изменить приведённую выше встроенную ассемблерную инструкцию: `asm volatile("mv a0, %0; ebreak" : :"r"(code));`. После этого изменения перед выполнением инструкции `ebreak` встроенная ассемблерная вставка сначала перемещает значение переменной `code`, представляющей статус завершения программы, в регистр `a0`.

<!--

For example, if `a0` is `0`, it outputs `HIT GOOD TRAP`, indicating that the program ended successfully; if `a0` is not `0`, it outputs `HIT BAD TRAP`, indicating that an error occurred in the program.
-->
С другой стороны, после того как NPC выполнит `ebreak`, среда симуляции может проверить значение регистра `a0`, чтобы понять, успешно ли завершилась программа. ## Add UART Support for Character Output
-->
## Добавьте поддержку UART для вывода символов

<!--
In Stage F, you have learned that users interact with the processor through input and output devices. In Stage F, sISA provides a dedicated `io` instruction for input and output. In RISC-V, however, input and output are performed through "Memory-mapped I/O". Specifically, RISC-V load and store instructions can access either memory or external devices. Which one is accessed is determined by the address range. minirv also adopts this approach.
-->
На этапе F вы узнали, что пользователи взаимодействуют с процессором через устройства ввода и вывода. На этапе F sISA предоставляет для ввода-вывода отдельную инструкцию `io`. В RISC-V же ввод и вывод выполняются через «ввод-вывод, отображённый на память» (Memory-mapped I/O). А именно: инструкции load и store в RISC-V могут обращаться как к памяти, так и к внешним устройствам. То, к чему именно происходит обращение, определяется диапазоном адресов. minirv также использует этот подход.

<!--
For example, suppose address `0x10000000` corresponds to the output data register of a serial port. Then the following instruction sequence can output the character `A` through the serial port:

```text
lui t0, 0x10000    # t0 = 0x10000000
addi t1, zero, 65  # 65 is the ASCII code of 'A'
sb t1, 0(t0)
```
-->
Например, предположим, что адрес `0x10000000` соответствует выходному регистру данных последовательного порта. Тогда следующая последовательность инструкций может вывести символ `A` через последовательный порт:

```text
lui t0, 0x10000    # t0 = 0x10000000
addi t1, zero, 65  # 65 is the ASCII code of 'A'
sb t1, 0(t0)
```

<!--
As you can see, the instruction sequence above is essentially no different from "writing the character `A` into memory". In C code, we can use a pointer to implement similar functionality:

```c
void putch(char c) {
  volatile char *p = (volatile char *)0x10000000ul;
  *p = c;
}
```
-->
Как видите, приведённая выше последовательность инструкций по сути ничем не отличается от «записи символа `A` в память». В коде на C мы можем реализовать похожую функциональность с помощью указателя:

```c
void putch(char c) {
  volatile char *p = (volatile char *)0x10000000ul;
  *p = c;
}
```

<!--
Here, `volatile` is a keyword in C. It tells the compiler not to optimize accesses through the corresponding pointer. Optimizing accesses to external devices usually leads to unexpected problems. We will discuss more details about `volatile` in later stages. For now, you only need to understand that when accessing external devices, you should add the `volatile` keyword in C code.
-->
Здесь `volatile` — это ключевое слово в C. Оно указывает компилятору не оптимизировать обращения через соответствующий указатель. Оптимизация обращений к внешним устройствам обычно приводит к неожиданным проблемам. Подробнее о `volatile` мы поговорим на более поздних этапах. Пока вам достаточно понимать, что при обращении к внешним устройствам в коде на C нужно добавлять ключевое слово `volatile`.

<!--


```c
}
```

<!--
The synthesis script contains multiple synthesis strategies, which are divided into three optimization objectives: delay optimization (`DELAY`), area optimization (`AREA`), and balanced delay-and-area optimization (`BALANCE`).
Each optimization objective contains several specific strategies. A particular strategy is selected using the format `optimization_objective index`. For example, the synthesis flow uses the `BALANCE 3` strategy by default. You can verify which strategy was used by checking the information printed at the beginning of the synthesis log.

Скрипт синтеза содержит несколько стратегий синтеза, разделённых на три оптимизационные цели: оптимизация задержки (`DELAY`), оптимизация площади (`AREA`) и сбалансированная оптимизация задержки и площади (`BALANCE`).

Например, поток синтеза по умолчанию использует стратегию `BALANCE 3`. Вы можете проверить, какая стратегия была использована, посмотрев информацию, выводимую в начале лога синтеза.
Число доступных стратегий для каждой оптимизационной цели можно определить, просто просмотрев упомянутый выше скрипт синтеза.

<!--

<!--
