# E7 Простая шина и SoC

<!--
You've designed processor NPC, and you understand how devices work.
-->
Вы уже спроектировали процессор NPC и понимаете, как работают устройства.

<!--
However, previously we let the simulation environment provide the behavioral models of devices. In real hardware, device controllers are RTL modules, and the processor should communicate with them through a purely hardware-based mechanism.
-->
Однако раньше мы позволяли среде симуляции предоставлять поведенческие модели устройств. В реальном железе контроллеры устройств — это RTL-модули, и процессор должен взаимодействовать с ними через чисто аппаратный механизм.

<!--
This mechanism is called a bus.
-->
Этот механизм называется шиной.

<!--
## Basic Concepts of Bus
-->
## Базовые понятия о шине

<!--
The essence of a bus is a communication protocol. It can exist in the communication between various modules.
-->
Суть шины — это протокол взаимодействия. Он может существовать в коммуникации между различными модулями.

<!--
For example, when a processor accesses memory, there is also a communication protocol between them.
-->
Например, когда процессор обращается к памяти, между ними также есть протокол взаимодействия.

```
+-----+         +-----+
| CPU | <-----> | MEM |
+-----+         +-----+
```

<!--
Generally, the module that actively initiates communication is called the **master**, while the module that responds to the communication is called the **slave**.
For example, in the above case, the processor is the **master**, and the memory is the **slave**.
-->
Обычно модуль, который активно инициирует взаимодействие, называется **ведущим устройством** (master), а модуль, который отвечает на взаимодействие, — **ведомым устройством** (slave).
Например, в примере выше процессор — это **ведущее устройство** (master), а память — **ведомое устройство** (slave).

<!--
In fact, bus design has two levels of meaning:
* At the protocol level, the master and slave need to reach an agreement on "how they communicate with each other".
* At the implementation level, when designing the interfaces between the master and slave, we need to use circuits to implement the details defined by the protocol.
-->
На самом деле у проектирования шины есть два уровня смысла:
* На уровне протокола master и slave должны договориться о том, «как они взаимодействуют друг с другом».
* На уровне реализации, проектируя интерфейсы между master и slave, нам нужно с помощью схем реализовать детали, определённые протоколом.

<!--
## System Bus
-->
## Системная шина

<!--
The bus that connects the processor with memory and devices is usually called the system bus.
In fact, we previously used the DPI-C to simulate the functionality of a system bus. NPC accessed memory through the DPI-C and interfaces such as `pmem_read()` provided by the simulation environment. In this process, there was no read latency: the read data could be returned in the same cycle when the read request was received.
However, this is only a convenient method for implementing communication in NPC. In reality, such a memory device does not exist.
-->
Шина, соединяющая процессор с памятью и устройствами, обычно называется системной шиной.
На самом деле мы ранее использовали DPI-C, чтобы симулировать функциональность системной шины. NPC обращался к памяти через DPI-C и такие интерфейсы, как `pmem_read()`, предоставляемые средой симуляции. В этом процессе не было задержки чтения: прочитанные данные могли быть возвращены в том же такте, в котором был получен запрос на чтение.
Однако это лишь удобный способ реализации взаимодействия в NPC. В реальности такого устройства памяти не существует.

<!--
Compared with the DPI-C, the biggest difference in memory access inside a real chip is that the access process has latency.
In other words, after the processor issues a read request, it needs to wait for several cycles before receiving the data returned by the memory.
This requires the processor to implement additional mechanisms:
-->
По сравнению с DPI-C, самое большое отличие обращения к памяти внутри реального чипа заключается в том, что процесс обращения имеет задержку.
Другими словами, после того как процессор выдаёт запрос на чтение, ему нужно подождать несколько тактов, прежде чем он получит данные, возвращённые памятью.
Это требует от процессора реализации дополнительных механизмов:

<!--
1. The processor needs to determine when the data returned by the memory becomes available.
2. Before the memory response arrives, the processor must wait. The processor can only continue executing the current instruction after receiving the returned data. This means that the processor can no longer maintain the property of executing one instruction per cycle.
3. Furthermore, instruction fetching does not need to happen every cycle. For example, while waiting for a memory response, the processor should not perform instruction fetching. Therefore, the processor needs to notify the memory when an actual instruction fetch operation should occur.
-->
1. Процессору нужно определять, когда становятся доступны данные, возвращённые памятью.
2. Пока ответ памяти не пришёл, процессор должен ждать. Процессор может продолжить выполнение текущей инструкции только после получения возвращённых данных. Это означает, что процессор больше не может сохранять свойство выполнения одной инструкции за такт.
3. Кроме того, выборка инструкции не обязана происходить каждый такт. Например, пока процессор ожидает ответа памяти, он не должен выполнять выборку инструкции. Поэтому процессору нужно уведомлять память о том, когда действительно должна происходить операция выборки инструкции.

<!--
However, real chips usually use industrial bus protocols similar to AXI, whose details are very complicated. For example, the AXI bus protocol contains more than 30 signals in total.
This means that, in principle, if we want a real chip to communicate with devices, we need to implement these bus protocols inside the processor.
To reduce the implementation burden, we will first introduce a simple custom bus protocol called SimpleBus.
-->
Однако реальные чипы обычно используют промышленные протоколы шины, похожие на AXI, детали которых очень сложны. Например, протокол шины AXI в общей сложности содержит более 30 сигналов.
Это означает, что в принципе, если мы хотим, чтобы реальный чип взаимодействовал с устройствами, нам нужно реализовать эти протоколы шины внутри процессора.
Чтобы снизить нагрузку реализации, мы сначала представим простой собственный протокол шины под названием SimpleBus.

Before implementing the bus, we will first briefly discuss processor performance evaluation.
-->
Прежде чем реализовывать шину, мы сначала кратко обсудим оценку производительности процессора.

<!--
### Accessing Read-Only Memory
-->
### Обращение к памяти только для чтения

<!--
Since reading data from memory is the most basic requirement, we will first consider how the processor performs read operations through the system bus.
-->
Поскольку чтение данных из памяти — самое базовое требование, мы сначала рассмотрим, как процессор выполняет операции чтения через системную шину.

<!--
Assume that the processor has a fixed specification of N\*32, meaning that the memory contains N addressable 32-bit locations. 
Also assume that the read latency of this memory is fixed at **1 cycle**. 
This is essentially a **synchronous memory**, where the delay between receiving a read request and returning the data is fixed. This behavior is consistent with the access characteristics of SRAM.
-->
Предположим, что процессор имеет фиксированную спецификацию N\*32, то есть память содержит N адресуемых 32-битных ячеек.
Также предположим, что задержка чтения этой памяти фиксирована и равна **1 такту**.
По сути это **синхронная память**, в которой задержка между получением запроса на чтение и возвратом данных фиксирована. Такое поведение соответствует характеристикам доступа SRAM.

<!--
If we do not consider write operations, we only need a ROM (Read-Only Memory).
To read data from the ROM, the corresponding bus only needs two signals: address and data. Their widths are `log2(N)` and `32`, respectively.
-->
Если не учитывать операции записи, нам нужна только ROM (постоянная память только для чтения).
Чтобы прочитать данные из ROM, соответствующей шине нужно всего два сигнала: адрес и данные. Их разрядности — `log2(N)` и `32` соответственно.

```
+-----+ raddr[log2(N)-1:0] ---> +-----+
| CPU | <---        rdata[31:0] | MEM |
+-----+                         +-----+
```

<!--
The communication protocol is:

* The master (CPU) sends the read address `raddr` to the slave (MEM).
* In the next cycle, the slave returns the data `rdata` to the master.
* The above behavior occurs every cycle.
-->
Протокол взаимодействия следующий:

* Master (CPU) отправляет адрес чтения `raddr` slave (MEM).
* В следующем такте slave возвращает данные `rdata` master.
* Описанное выше поведение происходит каждый такт.

<!--
Since instructions are stored in memory, IFU also needs to access memory during instruction fetch. 
At the same time, instruction fetching does not write data into memory, so a read-only memory is sufficient for the IFU to operate.
To simulate the delay introduced during memory access, after receiving an instruction fetch request, the memory cannot immediately return the fetched instruction. 
Instead, it must wait for one cycle before returning the instruction data.
According to the discussion above, for IFU, the SimpleBus involves the following signals:
-->
Поскольку инструкции хранятся в памяти, IFU также нужно обращаться к памяти при выборке инструкции.
При этом выборка инструкции не пишет данные в память, поэтому для работы IFU достаточно памяти только для чтения.
Чтобы симулировать задержку, вносимую при обращении к памяти, после получения запроса на выборку инструкции память не может сразу же вернуть выбранную инструкцию.
Вместо этого ей нужно подождать один такт, прежде чем вернуть данные инструкции.
Согласно обсуждению выше, для IFU SimpleBus включает следующие сигналы:

```verilog
output [31:0] ifu_raddr,
input  [31:0] ifu_rdata,
```

<!--
The timing of these signals is shown in the following diagram:
-->
Тайминг этих сигналов показан на следующей диаграмме:
```
           --\ /----------\ /----------\ /----------\ /----------\ /--
 ifu_raddr    X 0x80000000 X     (1)    X 0x80000004 X            X
           --/ \----------/ \----------/ \----------/ \----------/ \--
           --\ /----------\ /----------\ /----------\ /----------\ /--
 ifu_rdata    X            X 0x00000413 X     (2)    X 0x80051137 X
           --/ \----------/ \----------/ \----------/ \----------/ \--
```

<!--
To allow NPC to "wait for instructions returned from memory", we first need to let the IFU know which stage of the instruction fetch process it is currently in, and take different actions in different stages.
This kind of behavior, where different actions are performed at different times, can be implemented using a finite state machine (FSM) in digital circuits.
-->
Чтобы позволить NPC «ждать инструкции, возвращаемые памятью», нам сначала нужно, чтобы IFU знал, на какой стадии процесса выборки инструкции он сейчас находится, и предпринимал разные действия на разных стадиях.
Такое поведение, при котором в разное время выполняются разные действия, можно реализовать в цифровых схемах с помощью автомата состояний (FSM).

<!--
Specifically, we can implement two states for the IFU:

* `idle` state: Set `ifu_raddr` to `pc`.Then transition to the `wait` state.
* `wait` state: Use `ifu_rdata` as the valid instruction and continue execution.Then transition back to the `idle` state.
-->
А именно, мы можем реализовать для IFU два состояния:

* Состояние `idle`: установить `ifu_raddr` равным `pc`. Затем перейти в состояние `wait`.
* Состояние `wait`: использовать `ifu_rdata` как действительную инструкцию и продолжить выполнение. Затем вернуться в состояние `idle`.

<!--
According to the bus protocol described above, since communication occurs every cycle, the memory returns the data corresponding to the previous cycle's request while receiving the address request in the current cycle.
For example, in the figure above, when NPC sends a fetch request for address `0x80000004`, the memory simultaneously returns the data marked as `(2)`. This data corresponds to the address request marked as `(1)` in the previous cycle.
If NPC treats `(2)` as a valid instruction and executes it immediately, it will either execute the instruction at address `0x80000000` again or execute an instruction from another address. In either case, the behavior of NPC will no longer conform to the ISA specification.
Therefore, in the `idle` state, NPC should not treat `ifu_rdata` as a valid instruction. Instead, it should not execute any instruction.
-->
Согласно описанному выше протоколу шины, поскольку взаимодействие происходит каждый такт, память возвращает данные, соответствующие запросу предыдущего такта, одновременно с получением запроса адреса в текущем такте.
Например, на рисунке выше, когда NPC отправляет запрос на выборку по адресу `0x80000004`, память одновременно возвращает данные, отмеченные как `(2)`. Эти данные соответствуют запросу адреса, отмеченному как `(1)` в предыдущем такте.
Если NPC воспримет `(2)` как действительную инструкцию и сразу же выполнит её, он либо снова выполнит инструкцию по адресу `0x80000000`, либо выполнит инструкцию по другому адресу. В любом случае поведение NPC перестанет соответствовать спецификации ISA.
Поэтому в состоянии `idle` NPC не должен воспринимать `ifu_rdata` как действительную инструкцию. Вместо этого он не должен выполнять никакую инструкцию.

<!--
Previously, we assumed that NPC could execute one instruction every cycle. However, after introducing SimpleBus, NPC does not have a valid instruction to execute while waiting for the instruction response.
Therefore, we need to consider the question:"How can we make NPC stop executing instructions?"
Recall the state machine model of computer systems: the process of instruction execution is essentially the process of changing the processor state. In other words, if we can keep the processor state unchanged, we can achieve the effect of "not executing an instruction".
You should be able to think of the solution: the state of a processor is stored in sequential logic elements. As long as their write enable signals are disabled, the values of these sequential logic elements will not change.
Therefore, you also need to correctly configure the write enable signals of various sequential logic elements in NPC under the appropriate states.
-->
Ранее мы предполагали, что NPC может выполнять одну инструкцию за каждый такт. Однако после введения SimpleBus у NPC нет действительной инструкции для выполнения, пока он ожидает ответа на запрос инструкции.
Поэтому нам нужно рассмотреть вопрос: «Как заставить NPC прекратить выполнение инструкций?»
Вспомните модель автомата состояний компьютерных систем: процесс выполнения инструкции по сути является процессом изменения состояния процессора. Другими словами, если мы можем сохранить состояние процессора неизменным, мы можем добиться эффекта «невыполнения инструкции».
Вы наверняка уже догадались о решении: состояние процессора хранится в последовательностных логических элементах. Пока их сигналы разрешения записи отключены, значения этих последовательностных логических элементов не изменятся.
Поэтому вам также нужно правильно настроить сигналы разрешения записи различных последовательностных логических элементов в NPC в соответствующих состояниях.

<!--
### Accessing Readable and Writable Memory
-->
### Обращение к памяти для чтения и записи

<!--
Since the LSU needs to execute store instructions, we need to add new signals to the bus to support write operations:
-->
Поскольку LSU нужно выполнять инструкции store, нам нужно добавить в шину новые сигналы для поддержки операций записи:

<!--
* First, we naturally need a write address `waddr` and write data `wdata`.
* Since write operations do not occur every cycle, we also need to add a write enable signal `wen`.

  * Although read operations also do not occur every cycle (for example, in the multi-cycle NPC described above, no instruction fetch request is sent in the `wait` state), read enable is theoretically not required because read operations do not change the state of the circuit.
  * However, in practice, a read enable signal `ren` is usually still included. If there is no read request, the memory does not need to perform a read operation, which can reduce power consumption.
* A write operation may only modify some bytes within a word (for example, the `sb` instruction only writes 1 byte). Therefore, we also need to add a write mask signal `wmask`, which specifies which bytes in the write data should be written.
-->

* Поскольку операции записи происходят не каждый такт, нам также нужно добавить сигнал разрешения записи `wen`.

  * Хотя операции чтения тоже происходят не каждый такт (например, в описанном выше многотактном NPC в состоянии `wait` запрос на выборку инструкции не отправляется), разрешение чтения теоретически не требуется, поскольку операции чтения не изменяют состояние схемы.
  * Однако на практике сигнал разрешения чтения `ren` обычно всё же включают. Если запроса на чтение нет, памяти не нужно выполнять операцию чтения, что может снизить энергопотребление.
* Операция записи может изменять лишь некоторые байты внутри слова (например, инструкция `sb` пишет только 1 байт). Поэтому нам также нужно добавить сигнал маски записи `wmask`, который определяет, какие байты в записываемых данных нужно записать.

### More General Memory

### Более общая память

<!--
In fact, the property of a fixed one-cycle read latency can usually only be satisfied by SRAM. 
This is because SRAM can be manufactured using the same process technology as the processor. However, SRAM is very expensive.
To build lower-cost memory, other technologies with higher storage density are usually used, such as DRAM. 
Due to their electrical characteristics, the read latency of these memories is usually longer than the processor's one-cycle latency.
-->
На самом деле свойство фиксированной задержки чтения в один такт обычно может обеспечить только SRAM.
Это потому, что SRAM можно изготавливать по тому же технологическому процессу, что и процессор. Однако SRAM очень дорога.
Чтобы построить более дешёвую память, обычно используют другие технологии с более высокой плотностью хранения, такие как DRAM.
Из-за их электрических характеристик задержка чтения таких видов памяти обычно больше, чем однотактная задержка процессора.

<!--
In this situation, the processor cannot continuously send read requests. 
Otherwise, because the request rate of the processor is higher than the service rate of the memory, the memory will be constantly occupied by unnecessary requests, significantly reducing the efficiency of the entire system.
To solve this problem, the processor needs to tell the memory when a request is valid. 
Therefore, we can add a new signal `reqValid` to the signals sent from the processor to the memory. 
The memory can use this signal to determine when a real request exists. 
When the processor needs to access memory, it sets `addr` and other related signals, and sets `reqValid` to valid. 
When the processor does not need to access memory, it sets `reqValid` to invalid.
For the memory:
When `reqValid` is valid, it needs to access the data corresponding to `addr`.
When `reqValid` is invalid, the memory does not perform any access operation.
-->
В такой ситуации процессор не может непрерывно отправлять запросы на чтение.
Иначе, поскольку скорость запросов процессора выше скорости обслуживания памяти, память будет постоянно занята ненужными запросами, что значительно снизит эффективность всей системы.
Чтобы решить эту проблему, процессору нужно сообщать памяти, когда запрос действителен.
Поэтому мы можем добавить новый сигнал `reqValid` к сигналам, отправляемым процессором в память.
Память может использовать этот сигнал, чтобы определить, когда есть настоящий запрос.
Когда процессору нужно обратиться к памяти, он устанавливает `addr` и другие соответствующие сигналы и устанавливает `reqValid` в действительное значение.
Когда процессору не нужно обращаться к памяти, он устанавливает `reqValid` в недействительное значение.
Для памяти:
Когда `reqValid` действителен, ей нужно обратиться к данным, соответствующим `addr`.
Когда `reqValid` недействителен, память не выполняет никакой операции обращения.

<!--
On the other hand, when the memory can return data cannot be determined in advance.
For example, DRAM periodically refreshes the capacitors in its storage cells. If a read request arrives during the refresh process, the actual data read operation will only occur after the refresh is completed.
Therefore, the memory also needs to tell the processor when valid data can be returned.
Similarly, to identify when the memory response arrives, we can add a new signal `respValid` to the signals received by the processor from the memory. 
The processor can use this signal to determine when the memory response is valid.
-->
С другой стороны, заранее нельзя определить, когда память сможет вернуть данные.
Например, DRAM периодически обновляет конденсаторы в своих ячейках хранения. Если запрос на чтение приходит во время процесса обновления, фактическая операция чтения данных произойдёт только после завершения обновления.
Поэтому памяти также нужно сообщать процессору, когда можно вернуть действительные данные.
Аналогично, чтобы определить, когда приходит ответ памяти, мы можем добавить новый сигнал `respValid` к сигналам, получаемым процессором от памяти.
Процессор может использовать этот сигнал, чтобы определить, когда ответ памяти действителен.

<!--
Taking a read operation as an example:
When the memory has read out the data, it sets `rdata` and asserts `respValid`.
When the memory has not finished reading the data, it deasserts `respValid`.

For the processor:
When `respValid` is valid, it considers `rdata` to contain valid data.
When `respValid` is invalid, the processor considers that the data has not returned yet and continues waiting.
-->
Возьмём операцию чтения в качестве примера:

Когда память ещё не закончила чтение данных, она деактивирует `respValid`.

Для процессора:
Когда `respValid` действителен, он считает, что `rdata` содержит действительные данные.
Когда `respValid` недействителен, процессор считает, что данные ещё не вернулись, и продолжает ждать.

<!--
In real computers, common memory devices are usually volatile memory, such as SRAM and DRAM. They do not contain valid data after power-on.
If the CPU directly reads instructions from memory after power-on, the data returned by the memory is undefined. Therefore, the behavior of the entire system is also undefined, and the CPU cannot execute the expected program.
Therefore, a type of non-volatile memory is needed to store the initial program. Its contents can be preserved after power loss, allowing the CPU to immediately fetch instructions from it after power-on.
In ysyxSoC, the non-volatile memory is implemented using Flash, while the volatile memory is implemented using PSRAM. PSRAM is a special type of DRAM.
After integrating with ysyxSoC, NPC fetches its first instruction from Flash at address `0x30000000` after reset.
However, from the perspective of the processor, Flash cannot be directly written through memory access instructions. Therefore, programs usually need to be loaded from Flash into writable memory (such as PSRAM) before execution.
-->
В реальных компьютерах обычные устройства памяти, как правило, энергозависимы, например SRAM и DRAM. После включения питания они не содержат действительных данных.
Если CPU сразу после включения питания читает инструкции напрямую из памяти, данные, возвращённые памятью, не определены. Следовательно, поведение всей системы также не определено, и CPU не может выполнить ожидаемую программу.
Поэтому нужен тип энергонезависимой памяти для хранения начальной программы. Её содержимое может сохраняться после потери питания, что позволяет CPU сразу же выбирать из неё инструкции после включения питания.
В ysyxSoC энергонезависимая память реализована с помощью Flash, а энергозависимая память — с помощью PSRAM. PSRAM — это особый тип DRAM.
После интеграции с ysyxSoC NPC после сброса выбирает свою первую инструкцию из Flash по адресу `0x30000000`.
Однако с точки зрения процессора Flash нельзя напрямую записать инструкциями обращения к памяти. Поэтому программы обычно нужно загружать из Flash в записываемую память (например, PSRAM) перед выполнением.

Поэтому вы увидите вывод программы через последовательный порт, похожий на: `loading to memory region [0x80000000, 0x8004896c)`

Since we have integrated ysyxSoC, which contains a real UART controller, UART16550, some details of this UART controller are different from the simple UART behavioral model we implemented before.
As a result, the previously written `putch()` function cannot correctly access the real UART16550. This means that if we want to compile and run our own programs that can output characters, we need to further understand the details of UART16550 and modify `putch()` to support it.
-->
Поскольку мы интегрировали ysyxSoC, содержащий настоящий контроллер UART — UART16550, некоторые детали этого контроллера UART отличаются от простой поведенческой модели UART, которую мы реализовали ранее.
В результате ранее написанная функция `putch()` не может корректно обращаться к настоящему UART16550. Это значит, что если мы хотим компилировать и запускать собственные программы, способные выводить символы, нам нужно глубже разобраться в деталях UART16550 и изменить `putch()`, чтобы поддержать его.

<!--
In real chips, before a program outputs characters through a serial port, it needs to initialize the serial port first.
Specifically, the initialization process needs to configure the transmission parameters of the serial port, including:
baud rate;
character length;
whether a parity bit is used;
stop bit width.
Among these parameters, the `baud rate` refers to the number of characters transmitted per second.
-->
В реальных чипах, прежде чем программа выведет символы через последовательный порт, ей нужно сначала инициализировать последовательный порт.
В частности, процессу инициализации нужно настроить параметры передачи последовательного порта, включая:
скорость передачи (`baud rate`);
длину символа;
используется ли бит чётности;
разрядность стоп-бита.
Среди этих параметров `baud rate` означает число символов, передаваемых в секунду.

<!--
The transmitter and receiver must use exactly the same parameter configuration in order to correctly send and receive characters.
-->
Передатчик и приёмник должны использовать полностью одинаковую конфигурацию параметров, чтобы корректно отправлять и принимать символы.

<!--
A set of serial port parameters is usually described in a format such as `115200 8N1`. This means:
the baud rate is 115200;
the character length is 8 bits;
no parity bit is used;
the stop bit width is 1 bit.
-->
Набор параметров последовательного порта обычно описывается в формате вроде `115200 8N1`. Это означает:
`baud rate` равен 115200;
длина символа — 8 бит;
бит чётности не используется;
разрядность стоп-бита — 1 бит.

<!--
The data transmission process of `8N1` is shown below:
```txt
                                      stop ---+
                                              V
--------+   +---+---+---+---+---+---+---+---+---+--------
  idle  |   | D0| D1| D2| D3| D4| D5| D6| D7|      idle
        +---+---+---+---+---+---+---+---+---+    
          ^
 start ---+
```
-->
Процесс передачи данных `8N1` показан ниже:
```txt
                                      стоп ---+
                                              V
--------+   +---+---+---+---+---+---+---+---+---+--------
 покой  |   | D0| D1| D2| D3| D4| D5| D6| D7|      покой
        +---+---+---+---+---+---+---+---+---+    
          ^
 старт ---+
```

<!--
During idle periods, the serial line remains at a high level.
When a character needs to be transmitted, the UART first sends a start bit of 1-bit low level, then sends each bit of the character in order (the `D0`~`D7` bits shown in the figure), and finally sends a stop bit of 1-bit high level.
-->
В периоды простоя последовательная линия остаётся на высоком уровне.
Когда нужно передать символ, UART сначала отправляет старт-бит длительностью 1 бит на низком уровне, затем по порядку отправляет каждый бит символа (биты `D0`~`D7`, показанные на рисунке), и наконец отправляет стоп-бит длительностью 1 бит на высоком уровне.

<!--
The serial port can also be configured as `9600 7E2`, which means:
the baud rate is 9600;
the character length is 7 bits;
one even parity bit is used;
two stop bits are used.
If a parity bit is enabled, it is placed between the character bits and the stop bits.
-->
Последовательный порт также можно настроить как `9600 7E2`, что означает:
`baud rate` равен 9600;
длина символа — 7 бит;
используется один бит чётности (чётный);
используются два стоп-бита.
Если бит чётности включён, он располагается между битами символа и стоп-битами.

<!--
Due to electrical characteristics, in environments with long transmission distances and strong noise interference, the probability of successful character transmission decreases.
To improve the robustness of transmission against interference, UART protocols usually use oversampling techniques.
For example, when using 16× oversampling to detect the start bit, the signal needs to be sampled 16 consecutive times. Only when 8 or more consecutive samples are detected as low level will the UART consider the start bit to have been successfully detected.
-->
Из-за электрических характеристик в условиях больших расстояний передачи и сильных шумовых помех вероятность успешной передачи символа снижается.
Чтобы повысить устойчивость передачи к помехам, протоколы UART обычно используют технику передискретизации (oversampling).
Например, при использовании 16-кратной передискретизации для обнаружения старт-бита сигнал нужно выбрать 16 раз подряд. Только когда 8 или более выборок подряд определены как низкий уровень, UART сочтёт старт-бит успешно обнаруженным.

<!--
The baud rate also affects the probability of successful character transmission.
A higher baud rate means more characters can be transmitted per unit time. The transmission time of each character becomes shorter, and the sampling window for each character also becomes shorter, resulting in a higher bit error rate.
Conversely, a lower baud rate reduces the bit error rate, but software needs to wait longer when transmitting each character.
-->
`baud rate` также влияет на вероятность успешной передачи символа.
Более высокий `baud rate` означает, что за единицу времени можно передать больше символов. Время передачи каждого символа становится короче, а окно выборки для каждого символа также сокращается, что приводит к более высокой частоте битовых ошибок.
Наоборот, более низкий `baud rate` снижает частоту битовых ошибок, но программному обеспечению приходится дольше ждать при передаче каждого символа.

<!--
Since the UART controller cannot predict its future operating frequency, the baud rate is usually configured by software according to the actual operating frequency.
There is a ratio between the operating frequency and the baud rate, which indicates how many clock cycles are required to transmit one character.
Assume that the UART controller operates at 50 MHz:
If the baud rate is set to 115200, one character occupies:`50*1000000/115200 = 434` cycles.
If the baud rate is set to 9600, one character occupies:`50*1000000/9600 = 5208` cycles.
-->
Поскольку контроллер UART не может заранее знать свою будущую рабочую частоту, `baud rate` обычно настраивается программно в соответствии с фактической рабочей частотой.
Между рабочей частотой и `baud rate` есть соотношение, которое показывает, сколько тактов требуется для передачи одного символа.
Предположим, что контроллер UART работает на частоте 50 МГц:
Если `baud rate` установлен в 115200, один символ занимает: `50*1000000/115200 = 434` такта.
Если `baud rate` установлен в 9600, один символ занимает: `50*1000000/9600 = 5208` тактов.

<!--
Considering that UART uses oversampling, the UART controller needs to determine the sampling clock frequency.
This sampling clock is usually generated by dividing the UART controller's clock. Therefore, software needs to configure the clock division factor (or divisor) to indirectly set the baud rate.
For example, when the UART controller operates at 50 MHz and uses 16× oversampling, setting the baud rate to 115200 requires configuring the divisor register as:`50*1000000/115200/16 = 27.13`. 
This means that sampling occurs approximately every 27.13 clock cycles.
You can RTFM the UART documentation for more details about the relationship between the divisor and baud rate.
The UART manual is located at:`ysyxSoC/perip/uart16550/doc/UART_spec.pdf`
-->
Учитывая, что UART использует передискретизацию, контроллеру UART нужно определить частоту тактового сигнала выборки.
Этот тактовый сигнал выборки обычно генерируется делением тактового сигнала контроллера UART. Поэтому программному обеспечению нужно настраивать коэффициент деления тактового сигнала (divisor), чтобы косвенно задать `baud rate`.
Например, когда контроллер UART работает на частоте 50 МГц и использует 16-кратную передискретизацию, для установки `baud rate` в 115200 нужно настроить регистр divisor как: `50*1000000/115200/16 = 27.13`.
Это означает, что выборка происходит примерно каждые 27.13 такта.
Подробнее о соотношении между divisor и `baud rate` можно узнать, обратившись к документации UART (RTFM).
Руководство UART расположено по пути: `ysyxSoC/perip/uart16550/doc/UART_spec.pdf`

<!--
However, in hardware implementations, the divisor register usually only supports integer values.
For example, in the above case, the value written into the divisor register is usually `27`. The actual sampling interval then becomes `27/50MHz = 540ns`.
When the transmitter and receiver operate at different frequencies, this may introduce some transmission errors.
In such cases, changing the baud rate may help eliminate these errors.
-->
Однако в аппаратных реализациях регистр divisor обычно поддерживает только целые значения.
Например, в рассмотренном выше случае значение, записываемое в регистр divisor, обычно равно `27`. Тогда фактический интервал выборки становится равным `27/50MHz = 540ns`.
Когда передатчик и приёмник работают на разных частотах, это может вносить некоторые ошибки передачи.
В таких случаях изменение `baud rate` может помочь устранить эти ошибки.

<!--
The UART terminal in NVBoard is very simple. It only supports the `8N1` serial transmission configuration.

Терминал UART в NVBoard очень прост. Он поддерживает только конфигурацию последовательной передачи `8N1`.

Поскольку NVBoard — это среда программной симуляции, она не сталкивается с битовыми ошибками, вызванными электрическими характеристиками. Поэтому, в отличие от настоящего UART, она не использует техники передискретизации.
Divisor в NVBoard нельзя настроить во время выполнения, но его можно изменить, отредактировав исходный код.

### GPIO

<!--
NVBoard also provides devices such as LEDs and DIP switches, which we encountered in the F stage. Now we can make use of them as well.
Since the state of these devices can be transmitted through a single signal line, their functionality is relatively simple.
Generally, they can be connected through general-purpose pins on the chip. These pins are called GPIOs.
Through GPIOs, a chip can directly output internal signals to the outside of the chip, for example, to drive simple devices such as LEDs on a development board.
The chip can also use GPIOs to obtain simple external states, such as the status of DIP switches and buttons on the board.
-->
NVBoard также предоставляет такие устройства, как светодиоды и DIP-переключатели, с которыми мы уже встречались на этапе F. Теперь мы можем воспользоваться и ими.
Поскольку состояние этих устройств можно передать по одной сигнальной линии, их функциональность относительно проста.
Обычно их можно подключить через выводы общего назначения на чипе. Эти выводы называются GPIO.
С помощью GPIO чип может напрямую выводить внутренние сигналы за пределы чипа, например, чтобы управлять простыми устройствами вроде светодиодов на плате разработки.
Чип также может использовать GPIO, чтобы получать простые внешние состояния, такие как состояние DIP-переключателей и кнопок на плате.

<!--
ysyxSoC integrates a GPIO controller with an APB bus interface and maps it to the CPU address space `0x2000_1000 ~ 0x2000_100f`.
We allocate only 16 bytes of address space for the GPIO controller, which supports up to 128 pins. This is usually sufficient for typical applications.
-->
ysyxSoC интегрирует контроллер GPIO с интерфейсом шины APB и отображает его на адресное пространство CPU `0x2000_1000 ~ 0x2000_100f`.
Мы выделяем контроллеру GPIO всего 16 байт адресного пространства, что поддерживает до 128 выводов. Этого обычно достаточно для типичных приложений.

<!--

-->

## Adding Simple Control and Status Registers
-->
## Добавление простых регистров управления и статуса

<!--
In RISC-V, there is a class of system registers used to describe the processor state, called Control and Status Registers (CSR).
Through CSRs, we can add custom information to the hardware and allow programs to read this information during execution.
-->
В RISC-V есть класс системных регистров, используемых для описания состояния процессора, называемых регистрами управления и статуса (Control and Status Registers, CSR).
С помощью CSR мы можем добавить в аппаратуру произвольную информацию и позволить программам считывать эту информацию во время выполнения.

<!--
Unlike general-purpose registers, ordinary computational instructions cannot directly access CSRs.
Therefore, RISC-V provides CSR instructions for exchanging data between CSRs and general-purpose registers. Unlike ordinary instructions, CSR instructions atomically read and write the same CSR.
-->
В отличие от регистров общего назначения, обычные вычислительные инструкции не могут напрямую обращаться к CSR.
Поэтому RISC-V предоставляет инструкции CSR для обмена данными между CSR и регистрами общего назначения. В отличие от обычных инструкций, инструкции CSR атомарно читают и записывают один и тот же CSR.

<!--
CSR instructions use the I-type instruction format, so the CSR address space is 12 bits wide, containing 4096 possible addresses.
You can refer to the [RISC-V Privileged Architecture Manual][riscv priv manual] to learn more about CSR details.
However, we do not need to implement all CSRs. We only need to implement the CSRs that are required and perform read/write operations according to their CSR addresses.
Therefore, you do not need to understand every CSR described in the manual. You only need to refer to the relevant parts when needed.

[riscv priv manual]: https://riscv.github.io/riscv-isa-manual/snapshot/spec/#vol:priv
-->
Инструкции CSR используют формат инструкции I-типа, поэтому адресное пространство CSR имеет разрядность 12 бит и содержит 4096 возможных адресов.
Подробнее о деталях CSR можно узнать в [RISC-V Privileged Architecture Manual][riscv priv manual].
Однако нам не нужно реализовывать все CSR. Нам нужно реализовать только необходимые CSR и выполнять операции чтения/записи согласно их адресам CSR.
Поэтому вам не нужно разбираться в каждом CSR, описанном в руководстве. Вам нужно обращаться к соответствующим частям только по мере необходимости.

[riscv priv manual]: https://riscv.github.io/riscv-isa-manual/snapshot/spec/#vol:priv

### CSR счётчика тактов

<!--
Previously, we implemented clock functionality using a behavioral model. However, such a behavioral model does not exist in real chips.
RISC-V defines the `mcycle` CSR, which is a counter that increases by `1` every cycle.

В RV32, поскольку разрядность регистров общего назначения — 32 бита, этот счётчик разделён на два 32-битных CSR: `mcycle` и `mcycleh`.

В реальном чипе периферийные устройства обычно работают на относительно низких частотах из-за своих электрических характеристик.
Например, для [IS66WVS4M8ALL PSRAM][psram manual] максимальная рабочая частота для операций чтения в обычном режиме составляет 33 МГц. На более высоких частотах могут возникать нарушения таймингов, из-за которых PSRAM не сможет корректно читать данные.
С другой стороны, процессоры, изготовленные по современным техпроцессам, обычно могут работать на гораздо более высоких частотах.

<!--
To make full use of the processor's performance, an SoC typically includes a PLL (Phase-Locked Loop) to multiply the low-frequency clock supplied from outside the chip.
The high-frequency clock generated by the PLL is used to drive the processor, while the lower-frequency clock before frequency multiplication is used to drive the SoC and its peripherals.
Suppose the SoC and peripherals operate at 25 MHz and the PLL outputs a 500 MHz clock. Assuming that this high-frequency clock is within the NPC's maximum operating frequency range, the NPC should go through 20 cycles during one cycle of the PSRAM controller.

[psram manual]: https://www.issi.com/WW/pdf/66-67WVS4M8ALL-BLL.pdf
-->
Чтобы полностью задействовать производительность процессора, SoC обычно включает PLL (Phase-Locked Loop, петля фазовой автоподстройки частоты) для умножения низкочастотного тактового сигнала, подаваемого извне чипа.
Высокочастотный тактовый сигнал, генерируемый PLL, используется для тактирования процессора, а низкочастотный тактовый сигнал до умножения частоты используется для тактирования SoC и его периферии.
Предположим, что SoC и периферия работают на частоте 25 МГц, а PLL выдаёт тактовый сигнал 500 МГц. Если предположить, что этот высокочастотный тактовый сигнал находится в пределах максимальной рабочей частоты NPC, за один такт контроллера PSRAM NPC должен проходить 20 тактов.

[psram manual]: https://www.issi.com/WW/pdf/66-67WVS4M8ALL-BLL.pdf

### Эффективность симуляции

<!--
The `minirv-ysyxsoc` environment with a calibrated frequency ratio is well suited for performance evaluation, but you will also notice that its simulation efficiency is significantly lower than that of `minirv-npc`.
In terms of program execution time, `minirv-npc` can be tens or even hundreds of times faster to simulate than `minirv-ysyxsoc`.
This reflects a fundamental trade-off: to obtain more accurate performance data, you need to simulate more details, such as the bus, PSRAM controller, and frequency differences. This means that simulating each cycle requires more real-world computation time, ultimately reducing simulation efficiency.
Correspondingly, although `minirv-npc` has higher simulation efficiency, the performance data it produces is less accurate.
-->
Среда `minirv-ysyxsoc` с откалиброванным соотношением частот хорошо подходит для оценки производительности, но вы также заметите, что её эффективность симуляции значительно ниже, чем у `minirv-npc`.
По времени выполнения программы `minirv-npc` может симулироваться в десятки, а то и в сотни раз быстрее, чем `minirv-ysyxsoc`.
Это отражает фундаментальный компромисс: чтобы получить более точные данные о производительности, нужно симулировать больше деталей, таких как шина, контроллер PSRAM и различия частот. Это означает, что симуляция каждого такта требует больше реального времени вычислений, что в итоге снижает эффективность симуляции.
Соответственно, хотя `minirv-npc` обладает более высокой эффективностью симуляции, производимые им данные о производительности менее точны.

Если в `minirv-npc` есть функциональная ошибка, с высокой вероятностью та же ошибка есть и в `minirv-ysyxsoc`. Однако отлаживать ошибку в `minirv-npc`, где симуляция намного быстрее, очевидно более подходящий подход.
Таким образом мы можем в полной мере использовать сильные стороны обеих сред симуляции и компенсировать их соответствующие слабые стороны, тем самым повышая общую эффективность разработки и тестирования.
